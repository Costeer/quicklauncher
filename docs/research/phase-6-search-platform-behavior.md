# Phase 6 search platform behavior

Checked on 2026-09-14 against current first-party Android and GrapheneOS documentation and source. Accepted ADRs remain authoritative. This note records the platform rules needed by the Phase 6 adapters and their tests.

## Contacts

`READ_CONTACTS` is a dangerous runtime permission. Android says to request it only after the user starts the feature, check it again every time protected data is used, and keep the rest of the app usable after denial or revocation. The contacts provider must therefore stay disabled until an explicit enable action. Denial or later loss of the grant changes only the contacts provider to denied, cancels its current work, and removes its results. [Android runtime-permission workflow](https://developer.android.com/training/permissions/requesting)

Name search should use `Contacts.CONTENT_FILTER_URI` rather than loading the full contacts table. A provider query accepts a `CancellationSignal`, and `ContactsContract.LIMIT_PARAM_KEY` supplies a provider-side row limit for supported contacts URIs. The adapter still needs a local row cap because Android does not require every URI implementation to honor that parameter. Query on a worker dispatcher, request only required columns, close the `Cursor`, and connect coroutine cancellation to `CancellationSignal.cancel()`. [Contacts query guidance](https://developer.android.com/reference/android/provider/ContactsContract.Contacts) [contacts limit parameter](https://developer.android.com/reference/android/provider/ContactsContract#LIMIT_PARAM_KEY) [cancellable resolver query](https://developer.android.com/reference/android/content/ContentResolver#query(android.net.Uri,%20java.lang.String%5B%5D,%20android.os.Bundle,%20android.os.CancellationSignal))

Android keeps personal and managed-profile contacts in separate stores. Enterprise filter URIs can search the associated work profile, and `Contacts.isEnterpriseContactId()` identifies managed-profile rows. Quicklauncher may use an enterprise URI only after the host has classified the associated managed profile as eligible. If work is locked, quiet, unavailable, or ambiguous, it must use the personal URI and must not start a work query. A profile callback during an enterprise query cancels it, advances the host generation, and makes every row from the old query ineligible. [Work-profile contacts guide](https://developer.android.com/work/contacts) [enterprise contacts contract](https://developer.android.com/reference/android/provider/ContactsContract.CommonDataKinds.Phone#ENTERPRISE_CONTENT_URI)

Work contact lookup values are artificial but stable across queries only for the documented enterprise APIs. At activation, rebuild a lookup URI from the returned contact ID and lookup key, call `lookupContact()`, require a non-null current row, recheck contact permission and profile eligibility, and then use the system Quick Contact action. A missing row or lost grant performs no external action. [Contacts lookup contract](https://developer.android.com/reference/android/provider/ContactsContract.Contacts#getLookupUri(long,%20java.lang.String)) [work Quick Contact guidance](https://developer.android.com/work/contacts#show_a_contact)

GrapheneOS Contact Scopes deliberately presents the Contacts permission as granted while returning an empty or user-selected subset. It also hides account identity and can omit contact photos. Quicklauncher must accept that filtered view as the complete view available to the app. It must not diagnose an empty result as a broken grant, seek a second access path, or assume that a granted permission allows every contact. [GrapheneOS Contact Scopes](https://grapheneos.org/usage#contact-scopes)

Contact query strings, names, lookup keys, result text, and photos are session data. They do not belong in logs, diagnostics, fixtures, ranking history, backups, or provider preferences. The contacts adapter exposes only validated contract values and an opaque typed activation identity to the host.

## User-selected files

The Storage Access Framework is the access boundary. `ACTION_OPEN_DOCUMENT` grants access to chosen documents and `ACTION_OPEN_DOCUMENT_TREE` grants access only to a chosen subtree. Both actions use system UI and must start from an explicit user enable or configuration action. Quicklauncher does not request broad storage permission and does not crawl shared storage before the picker returns. [Storage Access Framework guide](https://developer.android.com/guide/topics/providers/document-provider) [shared-document access](https://developer.android.com/training/data-storage/shared/documents-files)

`ACTION_OPEN_DOCUMENT` returns a `content:` URI backed by a `DocumentsProvider`. Long-term access requires `takePersistableUriPermission()` with only the read mode actually granted by the result. Persisted grants survive reboot, but they are capabilities rather than proof that a document still exists. The adapter must intersect the returned flags with `FLAG_GRANT_READ_URI_PERMISSION`, reject other schemes and malformed URIs, and confirm the grant before reading display names, MIME types, sizes, or children. [open-document intent contract](https://developer.android.com/reference/android/content/Intent#ACTION_OPEN_DOCUMENT) [persisted URI permissions](https://developer.android.com/reference/android/content/ContentResolver#takePersistableUriPermission(android.net.Uri,%20int)) [document metadata contract](https://developer.android.com/reference/android/provider/DocumentsContract.Document)

Directory grants do not justify an unbounded recursive scan. Android warns that iterating a large selected tree can hurt performance, and Android 11 or newer prevents tree grants for storage roots, Download, `Android/data`, and `Android/obb`. Quicklauncher must cap roots, traversal depth, visited documents, results, metadata bytes, and elapsed time. It must use document-provider search only when the root declares that capability, with bounded traversal as the fallback. [tree access and restrictions](https://developer.android.com/training/data-storage/shared/documents-files#grant-access-directory)

A document provider can disappear, a user can release access, or a document can move or be deleted. Before activation, the adapter rechecks the persisted grant, queries a minimal projection, validates the current MIME type, and opens only the current `content:` URI through `ContentResolver`. `SecurityException`, `FileNotFoundException`, a null cursor, or provider failure becomes typed missing access or unavailable state and causes no external action. Removing or losing the last usable authorization disables only the file provider and removes its visible results. [DocumentsContract access requirement](https://developer.android.com/reference/android/provider/DocumentsContract) [persisted-grant inspection](https://developer.android.com/reference/android/content/ContentResolver#getPersistedUriPermissions())

GrapheneOS Storage Scopes is separate from a Storage Access Framework grant. It can make legacy storage permissions appear granted without exposing files created by other apps, while its file and directory choices still use the system picker. Quicklauncher should continue to rely on its own persisted picker grants and must not treat Storage Scopes as permission to index anything else. [GrapheneOS storage access](https://grapheneos.org/usage#storage-scopes)

File queries, display names, document IDs, result text, and retrieved bytes stay out of ranking history, logs, diagnostics, analytics, backups, and test fixtures. Durable state may retain only the minimum opaque authorization needed to reopen a user-selected root. It must not copy the root's labels or contents into preference records.

## Permission denial and revocation

Android distinguishes a first denial, a rationale state, and repeated denial where the system stops showing the dialog. `shouldShowRequestPermissionRationale()` is not a standalone permanent-denial detector because it is also false before the first request. The host needs its own typed record that a provider request was user-initiated, while the current framework grant remains the source of truth. Recovery can open application details after a denied request, but it must not loop permission prompts or block launcher startup. [Android denial behavior](https://developer.android.com/training/permissions/requesting#handle-denial)

Permission state can change without a provider request. Android can reset permissions for unused apps, and a revoked runtime permission can terminate the app process. Every query and activation must check the current grant. Foreground observers and Activity resume checks provide immediate cleanup when the process remains alive; normal composition and process recreation must reconstruct provider state from the framework and saved enabled-provider preference. [Android permission reset and revocation](https://developer.android.com/training/permissions/requesting#reset-unused-permissions)

A provider catches access races around each framework call. It does not catch coroutine `CancellationException` as denial or failure. Denial and revocation update only that provider's saved enabled state, close its active platform resources, and publish a provider-local denied state. Grant recovery starts a new generation and cannot revive results emitted by the old session.

Activity-result launchers for runtime permission and document access must register unconditionally during Activity initialization. Android's registry restores pending results across recreation and requires manual registrations to be unregistered when no longer needed. Only the host entry adapter owns these launchers. [Activity-result caller contract](https://developer.android.com/reference/androidx/activity/result/ActivityResultCaller#registerForActivityResult(androidx.activity.result.contract.ActivityResultContract,%20androidx.activity.result.ActivityResultCallback)) [Activity-result registry](https://developer.android.com/reference/androidx/activity/result/ActivityResultRegistry)

## Profile-aware search

`LauncherApps.getProfiles()` returns the profiles accessible to a launcher. On API 35 or newer, `getLauncherUserInfo()` supplies the user type and serial needed to distinguish managed and private profiles. Hidden private profiles require both the Home role and `ACCESS_HIDDEN_PROFILES`. A null launcher-user record means inaccessible, not personal. Quicklauncher must classify every handle and map it to a stable profile serial before calling `getActivityList()`, `getShortcuts()`, loading a label or icon, or opening a profile contact query. [LauncherApps profile APIs](https://developer.android.com/reference/android/content/pm/LauncherApps#getProfiles()) [LauncherUserInfo](https://developer.android.com/reference/android/content/pm/LauncherUserInfo)

Private Space has a strict search rule. Android requires a launcher to keep locked private apps invisible and undiscoverable through search. The system can still expose stale or partial launcher metadata during transitions, so profile policy must run before metadata collection and again before a result crosses the host boundary. Locked, quiet, hidden-entrypoint, stopped, inaccessible, or policy-ambiguous private profiles contribute no search result, cache record, ranking entry, fixture, or diagnostic value. [Android Private Space launcher requirements](https://developer.android.com/about/versions/15/behavior-changes-all#private-space) [Private Space entrypoint configuration](https://developer.android.com/reference/android/content/pm/LauncherUserInfo#PRIVATE_SPACE_ENTRYPOINT_HIDDEN)

Availability is asynchronous. `requestQuietModeEnabled()` does not mean the transition has finished, and Android provides generic profile available and unavailable broadcasts plus managed-profile equivalents. These broadcasts reach registered receivers, not manifest receivers. The host must listen while profile-sensitive search is alive, refresh the authoritative profile state, cancel affected provider work, advance the generation, and remove ineligible results in the next snapshot. Launcher package and shortcut callbacks also identify the affected `UserHandle`. [UserManager quiet mode](https://developer.android.com/reference/android/os/UserManager#requestQuietModeEnabled(boolean,%20android.os.UserHandle)) [profile broadcasts](https://developer.android.com/reference/android/content/Intent#ACTION_PROFILE_UNAVAILABLE) [LauncherApps callbacks](https://developer.android.com/reference/android/content/pm/LauncherApps.Callback)

Android provides `getUserBadgedIcon()` and `getUserBadgedLabel()` for managed-profile presentation. The latter adds an accessibility distinction such as a Work label. The platform adapter must apply the icon badge and accessible label before a work result leaves the host boundary. A presentation block must not invent or remove that distinction. [PackageManager work badging](https://developer.android.com/reference/android/content/pm/PackageManager#getUserBadgedLabel(java.lang.CharSequence,%20android.os.UserHandle))

Result identity includes the stable profile serial and target identity. Activation resolves that serial to a current `UserHandle`, reclassifies the profile, resolves the current app, shortcut, or contact target, and performs no side effect if any check differs from the result generation. Android advises persisting user serial numbers rather than `UserHandle` values because handles can be reused after user removal. [Android multi-user identification](https://developer.android.com/work/dpc/dedicated-devices/multiple-users#identification)

### Managed-profile test provisioning

Profile creation is not proof that a managed profile is usable. Android keeps a newly provisioned profile hidden until its profile owner enables it, and `ACTION_PROVISION_MANAGED_PROFILE` reports only synchronous setup success. Physical orchestration must complete every visible ManagedProvisioning page, then verify the profile type, owner, enabled state, and `RUNNING_UNLOCKED` state before starting profile-sensitive tests. [DeviceAdminReceiver completion contract](https://developer.android.com/reference/android/app/admin/DeviceAdminReceiver#onProfileProvisioningComplete(android.content.Context,%20android.content.Intent)) [managed-profile provisioning action](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#ACTION_PROVISION_MANAGED_PROFILE)

Android 8 and newer also deliver `ACTION_PROVISIONING_SUCCESSFUL` as an activity intent. Google's TestDPC handles it in a separate exported activity without the `BIND_DEVICE_ADMIN` permission, while its `ACTION_ADMIN_POLICY_COMPLIANCE` activity remains protected by that permission. Quicklauncher's debug-only physical-test DPC follows the same split and converges the success activity, compliance activity, and legacy receiver on idempotent synthetic initialization. This fixture architecture does not grant production code device-policy authority. [TestDPC manifest](https://github.com/googlesamples/android-testdpc/blob/master/src/main/AndroidManifest.xml) [TestDPC provisioning success activity](https://github.com/googlesamples/android-testdpc/blob/master/src/main/java/com/afwsamples/testdpc/provision/ProvisioningSuccessActivity.java) [Android provisioning-success contract](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#ACTION_PROVISIONING_SUCCESSFUL)

## Public Android Settings routes

The public settings provider should be a fixed catalog of documented `Settings.ACTION_*` values. Many documented actions explicitly warn that no matching Activity may exist. Package-specific routes such as `ACTION_APPLICATION_DETAILS_SETTINGS` require a `package:` URI. Quicklauncher must construct each intent from typed catalog fields, resolve it with `MATCH_DEFAULT_ONLY`, and catch `ActivityNotFoundException` and `SecurityException`. It repeats resolution immediately before activation. [Android Settings actions](https://developer.android.com/reference/android/provider/Settings) [intent resolution](https://developer.android.com/reference/android/content/pm/PackageManager#resolveActivity(android.content.Intent,%20int))

Resolution alone is not enough for an explicit or private component. The resolved `ActivityInfo` must be enabled, exported, owned by the expected package, and either have no access permission or require a permission Quicklauncher currently holds. `ActivityInfo.exported` states whether another app may use the component, and `ActivityInfo.permission` names its access permission. Failure falls back to the documented public parent, such as `ACTION_SETTINGS`, `ACTION_SECURITY_SETTINGS`, or application details. [ActivityInfo contract](https://developer.android.com/reference/android/content/pm/ActivityInfo)

The provider must not use Settings' internal search index, fragments, or controller classes. Those are not Android SDK contracts. Search terms map only to Quicklauncher's own static labels and typed route IDs. Route extras and data are fixed by the public API entry, never copied from provider result text.

## Versioned GrapheneOS Settings routes

GrapheneOS publishes source tags for its OS releases, and its Settings implementation changes across releases. There is no Android SDK promise for GrapheneOS-private actions or component names. The catalog therefore needs an explicit catalog version tied to reviewed GrapheneOS source and a bounded build or release range. It stays off until the user enables it. Unknown and newer builds receive public Android parents until their routes have been reviewed. [GrapheneOS release and source-tag policy](https://grapheneos.org/releases#about-the-releases) [GrapheneOS Settings source](https://github.com/GrapheneOS/platform_packages_apps_Settings)

The current branch shows why a string match is unsafe. `com.android.settings.DURESS_PASSWORD_SETTINGS` targets a non-exported Activity protected by `MANAGE_SAFETY_CENTER`. The per-app native-debugging and hardened-allocator activities are exported but protected by `WRITE_SECURE_SETTINGS`. A normal launcher cannot call any of them. Other private routes can be exported without that permission in the same revision, so the decision must inspect the exact resolved Activity rather than rejecting or accepting all GrapheneOS routes as a group. [GrapheneOS Settings manifest at reviewed commit](https://github.com/GrapheneOS/platform_packages_apps_Settings/blob/b637fa6fccd99fedc00d46de19cdff43def4b704/AndroidManifest.xml#L3376-L3388) [per-app GrapheneOS route declarations](https://github.com/GrapheneOS/platform_packages_apps_Settings/blob/b637fa6fccd99fedc00d46de19cdff43def4b704/AndroidManifest.xml#L6350-L6449)

For every catalog entry, build the exact action, package, component, data scheme, and fixed extras declared for that reviewed version. Before publishing and again before activation, require resolution to `com.android.settings`, an enabled and exported Activity, and no unheld permission. Catch launch races. A private failure never executes another component with the same action. It yields the entry's public Android parent. Quicklauncher does not request `WRITE_SECURE_SETTINGS`, `MANAGE_SAFETY_CENTER`, another signature permission, or Settings index access.

GrapheneOS adds Contact Scopes, Storage Scopes, a Network permission, and exploit-protection controls, but feature existence does not make a private deep link callable. Public Settings parents remain useful results even when every private route fails validation. [GrapheneOS features](https://grapheneos.org/features)

## Safe external web actions and URI validation

An external web search does not need to retrieve a page inside Quicklauncher. The safe default is a typed provider entry containing a reviewed HTTPS base destination and parameter name. At activation, the platform adapter builds a new hierarchical URI with `Uri.Builder` and `appendQueryParameter()`, which encodes the key and value. It never parses a result-supplied intent URI and never concatenates the raw query into a URL. [Uri.Builder encoding](https://developer.android.com/reference/android/net/Uri.Builder#appendQueryParameter(java.lang.String,%20java.lang.String))

Validation requires the exact `https` scheme, a nonempty allowlisted ASCII host, the expected port, no user information, no fragment, and a bounded path and encoded URI length. Reject `http`, `intent`, `javascript`, `data`, `file`, `content`, embedded intent syntax, credentials, control characters, malformed percent encoding, and any destination that changes the catalog host. Android's security guidance requires parsing and validating both scheme and host and warns that prefix, suffix, and substring host checks are unsafe. [Android unsafe-URI guidance](https://developer.android.com/privacy-and-security/risks/unsafe-uri-loading)

Open the validated URI with an `ACTION_VIEW` intent and `CATEGORY_BROWSABLE`. Resolve it immediately before launch and catch a missing handler. The action remains a user-visible external handoff. Search providers do not execute downloaded code, inject JavaScript, use a WebView, or retain the query after the action returns. [Android web intent guidance](https://developer.android.com/guide/components/intents-common#Browser)

If a reviewed provider later retrieves suggestion data, it needs a separate network adapter with a fixed HTTPS origin. Android recommends TLS and allows a network security configuration to reject cleartext traffic. `HttpURLConnection` defaults to following redirects and documents nonzero connect and read timeouts, so the adapter must set both timeouts, disable automatic redirects, validate each bounded redirect as a fresh HTTPS destination, and cap redirects. [Android network security guidance](https://developer.android.com/privacy-and-security/security-best-practices#network-security) [HttpURLConnection behavior](https://developer.android.com/reference/java/net/HttpURLConnection)

`Content-Length` does not bound the decoded response, especially with compression. Enforce a byte counter while reading, then apply bounded decoding and parsing depth, item count, and text length. Close the stream and disconnect on completion or coroutine cancellation. Oversize, redirect, parse, TLS, and timeout failures stay local to the web provider. The response cannot add commands, Android components, executable code, or arbitrary destinations. [HttpURLConnection response handling](https://developer.android.com/reference/java/net/HttpURLConnection#response-handling)

GrapheneOS can disable an app's Network permission and presents the failure to apps as if the network were down. A retrieved-data provider must map that behavior to unavailable or failed without prompting for an unrelated Android runtime permission. Other local providers continue normally. [GrapheneOS Network permission behavior](https://grapheneos.org/features#network-permission-toggle)

Web queries and results never enter history, logs, analytics, diagnostics, backups, or fixtures. Only static provider configuration and enablement may be durable.

## Lifecycle and coroutine restrictions

Search is foreground asynchronous work. Android does not guarantee that ordinary asynchronous work finishes after the app leaves a valid lifecycle state, and background activity launch restrictions make delayed external actions unreliable and disruptive. Quicklauncher must start external actions only from a current, explicit activation while the presentation is visible. It must not move search into a service, job, or process-wide contribution scope. [Android background-work guidance](https://developer.android.com/develop/background-work/background-tasks) [background activity launch security](https://developer.android.com/guide/components/activities/secure-bal)

One visible presentation owns one host search session. Removing the presentation closes the session and all provider sessions. Activity recreation saves only the bounded presentation input needed to reopen a fresh session. It does not preserve provider jobs or result objects. Compose `LaunchedEffect` cancels its coroutine when it leaves composition or its key changes, while `ViewModelScope` cancels when its ViewModel clears. The host still needs an explicit idempotent `close()` because a session can end before either owner clears. [Android lifecycle-aware coroutine scopes](https://developer.android.com/topic/libraries/architecture/coroutines)

Presentation collects immutable host snapshots with `collectAsStateWithLifecycle()` or `repeatOnLifecycle()`. A flow collection below the chosen active state is canceled and relaunched when active again. Parallel flows need separate child coroutines. Search retrieval should stop when the search UI is not visible rather than continuing inside a retained Activity or composition neighbor. [Lifecycle-aware flow collection](https://developer.android.com/topic/libraries/architecture/coroutines#lifecycle-aware)

Query replacement cancels the prior generation before provider fan-out for the next one. Each provider child runs under host failure isolation and a provider-local timeout. Framework adapters must bridge cancellation into their blocking primitive, such as `CancellationSignal` for provider queries, stream close plus `disconnect()` for HTTP, and callback unregistration for listeners. Cancellation propagates outward as cancellation, not a provider failure. Every emission carries current session and generation ownership, and the host drops stale or post-close output even if a platform callback arrives late.

## Implementation and test consequences

- Keep `Intent`, `Uri`, `Cursor`, `UserHandle`, `LauncherApps`, `CancellationSignal`, document APIs, and network connections inside host or platform entry adapters.
- Split personal contact search from enterprise contact search so an ineligible work profile is never touched.
- Check contacts permission, persisted document grants, profile eligibility, route callability, and external destination validity at query time and again at activation.
- Cancel profile and permission affected work immediately, increment the host generation, and publish a snapshot without those results.
- Apply the system work icon badge and accessible work label before contract results reach presentation.
- Keep public Settings parents available when the optional GrapheneOS catalog is disabled, unknown, stale, or uncallable.
- Test GrapheneOS route fixtures for non-exported, disabled, wrong-package, signature-permission, missing, callable, and changed-between-check-and-launch cases.
- Test Contact Scopes as an empty and partial successful contacts view, not only granted and denied Android permission states.
- Test file grants that disappear, providers that return malformed metadata, bounded tree traversal, and revocation during a visible query.
- Test cancellation at content query, cursor iteration, HTTP connect, response read, redirect validation, composition removal, Activity recreation, and session close.
- Treat authority-dependent device skips as skips. Physical tests must use synthetic contacts and files, restore all grants and profiles, and avoid recording labels, names, queries, document IDs, or returned content.
