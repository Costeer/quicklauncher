# Use a revisioned transactional launcher store

The host exposes a task-level, revisioned `LauncherStore` and keeps aggregate construction, Room entities, DAOs, row mapping, and the concrete Room adapter internal so callers cannot bypass atomic edits or launcher invariants. Android `Context` remains in `:host:platform`; it opens the store through a file-based factory that returns the small `CloseableLauncherStore` interface. The initial schema includes `Destination`, `DestinationLayout`, `ModuleInstance`, `ConfigurationDocument`, `Placement`, `ContentItem`, `FolderMember`, `AppOverride`, `WidgetPlacement`, `ThemeProfile`, `DestinationBackground`, and `CrashMarker`, accepting initially quiet tables to avoid later identity and relationship churn. The destination map stores a stable start reference, uses checked 64-bit coordinates, and enforces coordinate uniqueness and cardinal reachability. Module instances reference stable `ConfigurationDocumentId` values and own quarantine state; configuration replacement must complete the registered migration-and-decode path before new bytes become durable. Copies receive independent instance, configuration, placement, and layout-owned placement documents, and copied widgets require fresh host binding rather than reusing an Android widget ID. Shortcut identity is stored structurally as profile, package, and shortcut ID. Placement data remains opaque byte-preserving text with an explicit schema version, and Room plus Proto DataStore remain separate transactional domains, trading cross-store atomicity for clear storage ownership and requiring later multi-store operations to coordinate recovery explicitly.
