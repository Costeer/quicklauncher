Process audit / 2026-09-17

Quicklauncher is paying for context, over and over.

The agents are not wasting most tokens on prose. They are carrying very large working contexts through long implementation turns, repeated audits, full repository scans, test reruns, image payloads, and short interval polling. The fix is to bound work units and preserve evidence outside the conversation.

Why the agents burn tokens

The strongest causes are visible in both the session records and the repository's agent facing documents.

Broad goals run inside one turn for hours

The largest turn began after the user said a GrapheneOS device was attached. The agent inherited the full Phase 6 objective, worked for 4.6 hours, made 1,112 tool calls, and used 157.48M tokens. The final message describes an 88 file implementation and two full verification gates.

Long turns compound context cost because each model step sees the accumulated transcript. The average model step in this sample processed 118,350 input tokens.

Review is repeated as a workflow, not applied as a checkpoint

The local implement skill always hands completed work to code-review. That review always spawns standards and spec agents. The history adds audit, remediation audit, final audit, recheck, and post-fix review workers around the same large diffs.

Seventy completed review-family worker turns used 233.59M tokens. This excludes the root agent's coordination and remediation work, so it understates the full review loop cost.

Validation packets demand wide rereads

The Phase 6 validation prompt tells each reviewer to read every accepted ADR, long architecture and status documents, the full evidence report, research, contracts, CI, the current diff, and every listed untracked file. The named prose is roughly 15,000 words before source code and diff inspection.

The transcript contains 3,241 full file read patterns, 628 git diff mentions, and 304 git status mentions. Reopening the same large evidence base is expensive and makes the real acceptance criteria harder to find.

Tool results are returned at full size

Unique completed turns returned 96.3MB of tool data into context. Reads and searches account for 41.0MB. Images account for 15.6MB across only 59 calls because original resolution images are carried as base64. Gradle accounts for another 8.1MB.

Several visual reviews load multiple original resolution contact sheets. Large build and diff outputs then stay in the conversation for later model steps.

Build waits create model churn

The sample has 2,674 wait or poll outputs and 10.1MB of returned polling data. Exact one second polls recur dozens of times for the same process. Each poll can require another model step even when nothing useful changed.

Gradle setup is also repeated inline with long Nix store paths and environment exports. The transcript contains 1,141 Gradle command mentions and many near identical environment prefixes.

The fixed prompt is visible, but it is not the main problem

Base instructions are about 2,826 words in the recent sessions. That is worth pruning at the platform level, but it is small beside an average 118K token model input and it is usually cached. Cutting repository skill descriptions first would miss the expensive part.

The high value work is to shorten live transcripts, narrow the files each worker reads, and stop repeated verification.

Naive accounting multiplies shared history

T3Code fork and resume files include copied parent events. Summing each file's final cumulative total produces 7.80B tokens, more than five times the deduplicated result. Any dashboard built on file totals will point at the wrong sessions and hide whether changes worked.

Usage reporting must deduplicate by turn ID and use the change in cumulative counters during each turn.

Optimization plan

Apply these in order. The first two steps prevent another 157M token turn. Later steps reduce the cost of normal work.

1. Measure

Add a trustworthy usage report

  • Create tools/agent-usage-report.py. Read local Codex JSONL, keep the earliest owner of each turn ID, and calculate marginal input, cached input, output, duration, tool count, and tool output bytes.
  • Print top turns, root versus worker usage, review-family usage, and threshold breaches. Export JSON for later comparisons.
  • Record the current 1.492B pre-implementation sample as the audit baseline. Never sum transcript file totals.
Done when the script reproduces the figures in this report within rounding.
2. Bound

Turn phases into small execution packets

  • Give each packet one to three acceptance IDs, a narrow file area, focused tests, and an explicit packet acceptance condition.
  • At 8M recorded tokens, 75 model steps, 100 tool calls, or 45 minutes, record a compact checkpoint and delegate the next context-heavy slice. The main agent keeps ownership of the full request.
  • Never let a hardware status update resume an entire open phase. Resume only the blocked acceptance ID.
  • Keep each packet near 15 changed files. Split cross-cutting changes by contract, implementation, integration, and evidence when practical.
Done when the next phase has a packet manifest and no packet can silently expand to the whole phase.
3. Narrow

Replace full rereads with an acceptance index

  • Create a short phase brief that maps each acceptance ID to its governing ADR sections, contract sections, source paths, tests, and evidence.
  • Validation agents read the indexed sections for their assigned IDs. They open another ADR only when a concrete conflict points there.
  • Generate the changed file inventory with a command. Keep prose for decisions and evidence that commands cannot recover.
  • Keep the phase brief below 1,000 words. Move command logs and large manifests to machine readable artifacts.
Done when a worker can begin from one brief without reading every ADR and status document.
4. Delegate

Use depth-one workers for bounded context

  • Delegate every high-output operation to a subagent: work expected to produce more than 200 lines or 20 KB, including full builds or tests, broad searches, complete diffs, long logs or documents, and device matrices. Use parallel workers when their acceptance IDs or file areas are independent; do not impose a fixed worker count.
  • Use the two review axes once per release candidate. After fixes, rerun only the affected axis and focused tests.
  • Require subagents to save full evidence in files and report no more than 400 words to the main agent. Bounded-summary wrappers may run in the main agent.
  • Route simple mechanical file changes with exact acceptance criteria to lower-reasoning subagents when model choice is available.
  • Do not assign several workers to scan the same full diff. The root owns the shared inventory and hands each worker a slice.
  • The main agent owns integration and completion. Subagent reports are progress, not completion; there is no fixed subagent cap.
Done when every worker has a disjoint scope, reports compact evidence to the main agent, and the main agent integrates every result before completion.
5. Verify

Make test scope follow change scope

  • Run one focused test command while editing. Run the full local gate once after the packet set is integrated.
  • Run Paparazzi once for the release candidate. Inspect a single contact sheet at normal detail and reopen only changed or suspicious images.
  • Run each device matrix once when its prerequisite is present. Persist the serial, command, result, and repository state hash.
  • After a failure, rerun the failing task. Repeat the full gate only after a change that can affect the full gate.
Done when the verification ledger shows why each full gate was run.
6. Trim

Reduce command and result payloads

  • Add one repository command that supplies the JDK and Android SDK environment, so prompts stop repeating Nix store paths.
  • Write full build output to a temporary log. Return task counts, test counts, duration, status, and the failure tail.
  • Use bounded rg, line ranges, and file lists. Save large diffs to a file and inspect selected hunks.
  • Poll long commands every 20 to 30 seconds. Wait on workers for minutes, with asynchronous status updates, rather than one second loops.
  • Load image montages at normal detail. Use original detail only for a region where pixel accuracy decides the result.
Done when a comparable phase returns less than 30MB of tool output.

Method and evidence

The audit used local records and repository files. No network source or provider pricing table was used.

How usage was deduplicated

Session files were selected when their metadata named /home/costeer/git/quicklauncher as the working directory.

Forked and resumed files contain copied history. Each completed turn_id was assigned to the earliest transcript containing its start event. Usage sums each positive change in the cumulative counters. When compaction resets a counter, accumulation restarts from the new value.

Incomplete and aborted turns were excluded. The current audit turn is not in the sample.

What the token fields mean here

total_tokens equals input plus output in these records. Reasoning output is a subset of output and is not added again. Cached input is shown as a share of input.

The records report 1,488,155,597 input tokens, 1,452,319,232 cached input tokens, 3,740,564 output tokens, and 1,491,896,088 total tokens.

Repository sources inspected

implement skill, code review skill, Phase 6 validation prompt, Phase 7 validation prompt, current state, accepted ADRs, phase evidence, architecture, contracts, research, CI, and the local skill catalog.

Limits of the analysis

The audit measures recorded tokens, not money. It does not assign tokens to individual repository files. Tool output bytes are serialized transcript size, so image base64 and wrapper metadata are included. The review-family classification uses worker path names containing terms such as review, audit, recheck, final, requirements, or checklist.
